# GitHub Pages + Discord: что проверено и что получилось

Коротко: **обе задачи решаются, своего сервера писать не нужно.** Ниже —
что именно ограничивает GitHub Pages, где эти ограничения обходятся и какой
ценой.

## 1. GitHub Pages

Pages отдаёт статические файлы и больше ничего: ни выполнения кода на
сервере, ни переменных окружения в рантайме, ни секретов. Для этой страницы
этого достаточно — весь интерфейс собирается в браузере.

Что пришлось учесть:

| Ограничение | Решение |
| --- | --- |
| Project site живёт по пути `/<репо>/`, а не в корне домена | `base` в `vite.config.ts` берётся из `BASE_PATH`, который workflow подставляет из имени репозитория |
| Нет серверного роутинга: неизвестный путь → 404 | Приглашение читается из хеша (`#/join/<guid>`) или query (`?invite=...`) — обе формы отдаёт один и тот же `index.html` |
| Jekyll съедает файлы и папки с подчёркиванием | Пустой `public/.nojekyll` |
| Секретов в сборке быть не может | В клиент попадает только публичный anon-ключ Supabase; всё остальное закрыто политиками в БД |
| HTTP-заголовков не задать, в том числе CSP | Политика собирается в `vite.config.ts` (адрес Supabase известен только на сборке) и уезжает мета-тегом в `index.html`. Мета-тег не умеет `frame-ancestors` — запретить встраивание страницы в чужой iframe так нельзя |

Сборка деплоится через `actions/deploy-pages` (`.github/workflows/deploy.yml`).
Демо-сборка без бэкенда — 13 КБ gzip.

## 2. Авторизация через Discord

Здесь и лежит единственная настоящая сложность. Discord OAuth2 в обычном,
безопасном варианте требует обмена кода на токен с `client_secret` — а
секрет невозможно положить в статическую страницу. Варианта два.

**Implicit grant (`response_type=token`) — работает без секрета, но не
годится.** Токен приезжает прямо в адресную строку, и проверить его
некому: без серверной стороны любой может обратиться к хранилищу напрямую,
представившись кем угодно. Для страницы с общими данными пачки это значит
отсутствие какой-либо защиты.

**Supabase Auth — то, что используется здесь.** Обмен кода на сессию идёт
на серверах Supabase: `client_secret` Discord хранится в настройках проекта
и в репозиторий не попадает. Клиент получает подписанный JWT, по которому
Postgres через RLS решает, что человеку можно читать и писать. Фронтенд
остаётся полностью статическим, своего кода на сервере — ноль.

Поток входа:

```
ссылка с GUID  →  GUID в localStorage  →  Discord OAuth (PKCE)
                                              ↓
   страница опроса  ←  join_pack(GUID)  ←  возврат на Pages с ?code=
```

GUID переживает редирект через `localStorage`, а не через адрес: Supabase
возвращает пользователя на фиксированный `redirectTo` из белого списка, и
складывать туда переменную часть не нужно.

## 3. Авторизация по GUID приглашения

`packs.invite_code` — это `uuid v4` со значением по умолчанию
`gen_random_uuid()`. Ссылка выглядит так:

```
https://<юзер>.github.io/<репо>/#/join/3f2a9c10-....
```

Правила доступа (`supabase/schema.sql`, проверены тестом
`supabase/test/run.sh`):

- **до входа** анонимный ключ может вызвать ровно одну функцию —
  `pack_preview(guid)`, которая отдаёт название и игру, чтобы на экране
  входа было видно, куда зовут. Больше анонимному ключу не доступно ничего,
  включая таблицу `packs`;
- **вступление** идёт только через `join_pack(guid)`. Прямая запись в
  `pack_members` запрещена политикой, так что без действующего GUID в пачку
  не попасть;
- **внутри пачки** участники видят ответы друг друга — иначе не построить
  тепловую карту и не посчитать голоса, — но писать могут только свои
  строки (`user_id = auth.uid()`);
- **повторный заход по ссылке** безопасен: `join_pack` идемпотентна и
  заодно обновляет имя и аватар из Discord.

Чего эта схема **не** делает: GUID не одноразовый и не протухает. Кто угодно
с ссылкой войдёт в пачку. Для компании друзей это ровно то, что нужно;
если понадобится иначе — в `packs` добавляется `invite_expires_at` или
таблица одноразовых приглашений, клиент при этом не меняется.

## 4. Почему такой стек

| Слой | Выбор | Почему |
| --- | --- | --- |
| Сборка | Vite + TypeScript | один конфиг, `npm run build` → статика; типы ловят ошибки в датах, агрегации карты и расчёте душноты |
| UI | без фреймворка | страница одна; узлы строятся один раз, состояние перекрашивает их на месте — это нужно, чтобы протяжка по часам не теряла `pointerenter` на пересозданных узлах |
| Данные и вход | Supabase | единственный слой, который закрывает и OAuth-обмен, и хранилище с правами, не требуя писать сервер |
| Хостинг | GitHub Pages | бесплатно, деплой из того же репозитория |

Рантайм-зависимость ровно одна — `@supabase/supabase-js`, и та грузится
отдельным чанком только когда бэкенд настроен.

## 5. Два режима работы

Сборка смотрит на `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`:

- **переменные не заданы** → демо-режим. Ответы девяти участников
  генерируются детерминированно, свои сохраняются в `localStorage`, входа
  нет. Страница целиком рабочая — это и есть подтверждение, что вёрстка и
  логика живут на Pages без бэкенда;
- **переменные заданы** → боевой режим: вход через Discord, общие данные,
  права по RLS.

Переключение — только пересборка, кода это не касается
(`src/backend/index.ts`).

## 6. Что осталось за рамками

- **Создание пачек.** По ТЗ его в этой версии нет: пачка заводится вручную
  через `supabase/seed.sql`.
- **Живое обновление.** Чужие ответы подтягиваются при загрузке страницы.
  Supabase Realtime добавляется подпиской на те же таблицы, схема готова.
- **Живой профиль.** Имя и аватар обновляются при загрузке (`sync_profile`),
  а не в реальном времени.
